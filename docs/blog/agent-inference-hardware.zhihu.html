目前单个SM的架构已经逆向得差不多了，接下来的重点来到调度以及整个推理系统。

目前云端Agent的任务负载其实非常复杂，编程 Agent 会反复读文件、生成代码、运行命令、等待测试，再根据结果继续工作，一次任务可以持续很多轮，中间还会启动子 agent，服务端看到的流量因此带有很强的时间关系，有些请求必须等前面的请求结束，有些分支同时运行，有些会话几分钟没有新请求，上下文却可能在下一轮继续使用。

这种负载情况跟分析单卡的时候完全不一样，端侧可能跑个几十k的上下文，一般也就单batch，复杂程度其实要低很多，云端需要同时考虑模型结构、请求时序、缓存状态、部署方式和软件实现，算力、存储容量、存储带宽、互联带宽与通信延迟，他们各自影响不同的过程，一个具体部署能发挥出多少性能，还取决于推理框架怎样调度这些过程。

我们这里直接看 AgentX 的负载，它里面给出了claude code的trace，符合绝大多数用户真实的使用情况。

0x01 Agent 请求具有怎样的结构

先看一个简化的编程任务，主 agent 读完项目后，分别让两个子 agent 查找调用链和分析测试，两个分支各自调用模型、执行工具，主 agent 在需要它们的结果时等待，随后生成修改方案。

每个“调用模型”的节点里面，还包括排队、prefill 和 decode，图上的边则可能包含工具执行时间、用户思考时间，以及分支之间的依赖。

这样的负载至少有几个值得分别观察的量，每轮完整输入有多长，其中多少内容可以复用，每轮需要生成多少 token，相邻请求之间隔多久，同时活跃的分支有多少，会话何时结束或压缩上下文，例如，测试产生大量日志后，下一轮输入会突然增长，子 agent 从同一个项目背景分叉，可能共享很长的前缀。

把它们各自抽成一个独立的平均数，会丢掉不少信息，两个请求平均都是 128K 上下文，可能分别来自“两个 128K 请求”，也可能来自“一个很短的请求加一个接近 256K 的请求”。它们对长上下文 kernel、缓存分配和批处理尾部的影响未必相同。

工具等待也影响硬件需求，某个会话暂时没有占用计算资源，保留它的历史状态仍然可能消耗存储，多个会话的等待可以错开，让设备持续工作，也可能因为相似的工具任务同时结束，形成一阵新的请求，单个 session 的等待比例无法直接换算成 GPU 的空闲比例。

会话结束也不必然立刻释放所有缓存。前缀缓存可能被保留用于后续命中。反过来，一个仍然存活的会话也可能因容量不足被淘汰，下一轮恢复时重新加载或计算。

因此，有必要同时画出逻辑上下文、物理驻留量和活动工作集。活动工作集描述某段时间内真正被访问的数据，驻留量描述当前占着存储的数据，它们的差距正是分层存储可能发挥作用的地方。

命中率的变化会放大重算量。输入量固定、未命中的 token 都需要重算时，命中率从 98% 降到 97%，重算量会从 2% 变成 3%，增加 50%。这只是算术例子，真实时延还取决于缺失位置、请求分布和执行效率。

多级缓存还要看写入策略。写穿透会让上下两层同时保存一份数据；另一种实现可能只把被逐出的状态写到下层。两种方式对容量、写入流量和命中统计的影响不同，应该由软件配置明确下来。

资源配比要结合负载来看。prefill 池太小，请求会堆在首轮计算之前；decode 池太小，生成时间会变长，已经建立的状态也会驻留更久。两边的服务率随 batch 和上下文分布变化，不能只按总输入 token 与总输出 token 的比例配卡。

异构系统可以让 prefill、decode 和下层存储使用不同器件。建模时，各组引用自己的算子时延表和存储层次，再用状态交付把它们连接起来。两端格式不一致时，还要把转换算子和转换时间算进去。

还可以把同一层中的 attention 和专家计算分到不同设备，这会增加高频交互，尤其要计算每层的固定通信成本。阶段级、层级和存储级异构应该分开研究，不能默认它们有相同的通信代价。

系统规模也要一起看。新增设备可能增加容量和并行度，也可能改变通信域、复制关系和调度方式。把单卡预测直接乘设备数，只适用于资源和工作可以近似独立扩展的区域。

0x0C 软件、CPU 与器件内部的执行效率

调度器决定什么时候让就绪请求进入执行，以及一轮带多少 token。continuous batching 会在迭代之间调整成员；chunked prefill 把长输入拆成多个片段；token budget 和请求数上限限制单次 batch。

这些开关会直接改变算子的 shape。更大的 prefill chunk 可能提高矩阵运算效率，同时延长同一 worker 上其他请求的等待；抢占可以腾出容量，但恢复被抢占请求时还要处理它的状态。

KV 感知路由也有取舍。把会话留在原 worker 上，局部命中可能更高；原 worker 过载时，迁移可能减少排队，却增加搬运或重算。路由策略需要同时看缓存位置和服务负载。

CPU 侧的前缀查询、请求组织、采样和流式返回也会消耗时间。InferenceX 对 MiniMax-M3 的分析指出，所研究配置中的 Dynamo 路由工作量会随存活前缀的数量和长度增长，可能成为瓶颈；宽并行 kernel 和 offload 支持也会限制系统表现。这个案例说明，硬件模型不能只写 GPU kernel。 MiniMax-M3 系统案例

算子内部也要拆开看。矩阵单元以外，归一化、激活、索引、top-k、归约、转置和量化转换会使用其他执行资源；片上存储决定能保留哪些数据，数据布局影响能不能有效喂给计算单元，DMA 和通信引擎还会影响搬运与计算能否重叠。

所以，即使两种器件的标称 FLOPS 和主存带宽相同，执行这些模块的效率也可能不同。成熟 kernel 可能把多个操作融合起来，新器件上则可能暂时分开执行。

系统模型可以先把一部分 host 和启动开销表示成每步固定开销，但它只覆盖标定时的规模范围。如果路由成本随活跃会话数或前缀长度变化，就应该把它写成变量的函数，必要时还要加入 CPU 服务队列。

通信实测表和模块级时延表可能已经包含部分同步或内部拷贝。组合模块前要先确认每张表从哪里开始计时、到哪里结束，否则容易重复计算。

更长的草稿可能提高矩阵运算效率，也可能增加被拒绝的计算。高并发下，普通 decode 已经有较好的批处理，继续增大验证 batch 的收益可能变小，低并发结论不能直接套到高吞吐区域。

投机解码也会改变 token 到达的节奏。一次提交多个 token，再等待下一次验证，和每隔固定时间均匀输出 token，在平均吞吐相同时，用户感受到的节奏仍然不同。因此要保留请求级时间信息，不能只保存一个平均 tokens/s。

分母也可以换成满足响应要求的输出吞吐，或者完成的有效任务数。后者还需要任务质量和工作流数据；输入、输出和缓存命中的计费规则各不相同，服务成本不能直接等同于 API 售价。

功耗应该覆盖整套被占用的资源。一张卡在某个阶段等待，不代表它不耗电，也不代表它的购置成本可以忽略。如果有状态级功耗数据，可以把计算、访存、通信和等待阶段的能量积分起来；只用 TDP，则是另一种近似。

设计空间还受物理约束。主存带宽、容量、互联端口、片上存储、计算阵列和封装成本往往相互关联；增加内存通道，可能同时增加容量、带宽、PHY 面积和功耗，增加互联资源也会占用芯片和封装资源。

所以，反过来问“需要多少带宽才能达到目标”时，必须把条件写出来：使用什么模型、多少设备、哪些并行方式、怎样的存储容量和软件能力，以及带宽变化时哪些参数会一起变化。

如果把所有参数都当成可以独立调大的旋钮，会得到无法实现的配置。粗粒度模型可以接受用户给出的耦合约束，再在这些约束内寻找可行区域。

0x0F 一个系统模型怎样组织

前面这些问题可以组织成几个相互连接的层次：负载层描述请求和依赖，状态层管理缓存和执行队列，单步层生成当前要执行的算子与通信，底层负责估计这些操作的时延。

一次事件驱动仿真可以这样推进：取出最近的事件，更新已经完成的计算或搬运；让满足依赖的请求进入就绪队列；按容量和策略准入请求；为可以运行的 worker 组 batch，计算下一次完成时间，然后把虚拟时钟推进到下一个事件。

仿真时要保留每个请求的新 token 数、历史长度和状态位置。不同算子可以用不同的聚合方式：共享线性层关注本轮 token 总数，attention 关注每个请求的上下文，MoE 关注路由后的专家负载。

单步时延由依赖图决定。串行操作相加，能够并行且资源足够的分支按完成时刻汇合；两个模块可以重叠，也不代表它们都能按独占资源时的速度完成，如果共享带宽、计算资源或缓冲区，就要把这种竞争写进模型。

为了快速探索，可以先用闭式模型估算容量要求以及计算、访存、通信的下界，淘汰明显不可行的配置，再对剩余候选执行事件重放。把相同 shape 的算子查询缓存起来，也能减少模型运行时间。

硬件、互联、部署映射和软件栈最好分别描述。这样既能比较相同软件能力下的硬件变化，也能比较各系统当前实际可用的部署，后一种结果会包含软件成熟度的影响。

DLsim 采用 device、fabric、mapping、stack 四类配置，把算子时延、单步时延和状态引擎分开。现在这篇文章讲的是接口和建模方法，后面的模型还要继续写成具体的算子与状态描述，不能用旧模型的参数直接替换。

0x10 怎样验证，以及哪些问题仍需额外数据

验证可以从单个算子开始，再逐步组合到系统。精确命中的查询应该返回原始测量；插值要在留出的 shape 上检查；跨器件外推要用没有参与拟合的器件验证。每种误差都要注明自己的适用范围。

到了单步层，可以检查某个 batch 的实际算子清单、并行后的形状、通信消息和执行依赖。系统层则要看吞吐、TTFT、生成时延、各级缓存命中和并发曲线能不能同时得到解释。

只拟合最终吞吐，并不能说明内部过程是对的。低估计算、同时高估通信，可能刚好得到相近的总时间；一旦改变 batch 或拓扑，两项误差不再抵消，预测就会偏离。

资源记录有助于诊断，但先要把口径说清楚。计算和通信可能重叠，所以占用率相加超过 100% 并不奇怪；容量不足通常通过排队、淘汰、重算或限制 batch 影响时间，不能把“容量受限”直接当成一种可以独立相加的执行时间。

因此，既要保存各资源的占用和排队状态，也要做有明确条件的参数扰动：增加容量后缓存和时延怎样变化，只提高链路带宽后哪段路径缩短，更换路由策略后命中率和负载如何重新分布。这样才能判断模型是否给出了可解释的响应。

数据用途也要区分。已经参与分析和参数选择的点可以作为开发诊断；要检验预测能力，就要保留没有参与这些选择的数据，并在比较前确定配置、指标和误差口径。如果模型后来修改，修订前后的结果都应该保留。

误差还可能是相关的。同一个 kernel 在所有层上都被低估，不会因为层数多就自然抵消；相同的固定开销误差还会反复影响每个 decode step。最终区间应该反映这些系统性误差，不能只把每层当成独立噪声。

近期模型还会带来新的硬件问题。视觉 Agent 需要图像或视频编码、特征缓存和不同长度的视觉 token；长时间任务会压缩上下文或恢复历史检查点；多模型系统可能给不同节点选择不同模型。这些过程可以继续扩展到请求图和状态模型，但需要对应的负载数据。

真实系统里的网络、工具执行和任务质量也可能随部署变化。固定 trace 重放通常把工具时间和请求结构当成给定条件，用来研究这些条件下的服务性能；换一个模型后，它可能生成更多推理 token、调用不同工具或减少重试，这类行为变化需要新的轨迹或明确的行为假设。
