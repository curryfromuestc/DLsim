编程 Agent 会反复读文件、生成代码、运行命令、等待测试，再根据结果继续工作。一次任务可以持续很多轮，中间还会启动子 agent。服务端看到的流量因此带有很强的时间关系：有些请求必须等前面的请求结束，有些分支同时运行，有些会话几分钟没有新请求，上下文却可能在下一轮继续使用。

讨论这类推理的硬件，需要同时考虑模型结构、请求时序、缓存状态、部署方式和软件实现。算力、存储容量、存储带宽、互联带宽与通信延迟，各自影响不同的过程。一个具体部署能发挥出多少性能，还取决于推理框架怎样调度这些过程。

本文结合 AgentX 的公开负载、InferenceX 的系统测量，以及近期开放模型的结构，讨论这些问题怎样描述、计算和验证。资料查阅时间为 2026 年 9 月 20 日。涉及已有实测的地方附原始来源；文中的演算示例会注明假设。DLsim 目前处于设计阶段，下面涉及它的部分描述拟采用的建模方法。

1. Agent 请求具有怎样的时间结构

先看一个简化的编程任务。主 agent 读完项目后，分别让两个子 agent 查找调用链和分析测试。两个分支各自调用模型、执行工具，主 agent 在需要它们的结果时等待，随后生成修改方案。

每个“调用模型”的节点里面，还包括排队、prefill 和 decode。图上的边则可能包含工具执行时间、用户思考时间，以及分支之间的依赖。

这样的负载至少有几个值得分别观察的量：每轮完整输入有多长，其中多少内容可以复用；每轮需要生成多少 token；相邻请求之间隔多久；同时活跃的分支有多少；会话何时结束或压缩上下文。这些量通常相关。例如，测试产生大量日志后，下一轮输入会突然增长；子 agent 从同一个项目背景分叉，可能共享很长的前缀。

把它们各自抽成一个独立的平均数，会丢掉不少信息。两个请求平均都是 128K 上下文，可能分别来自“两个 128K 请求”，也可能来自“一个很短的请求加一个接近 256K 的请求”。它们对长上下文 kernel、缓存分配和批处理尾部的影响未必相同。

工具等待也影响硬件需求。某个会话暂时没有占用计算资源，保留它的历史状态仍然可能消耗存储。多个会话的等待可以错开，让设备持续工作；也可能因为相似的工具任务同时结束，形成一阵新的请求。单个 session 的等待比例无法直接换算成 GPU 的空闲比例。

因此，有必要同时画出逻辑上下文、物理驻留量和活动工作集。活动工作集描述某段时间内真正被访问的数据，驻留量描述当前占着存储的数据，它们的差距正是分层存储可能发挥作用的地方。

多级缓存的组织同样重要。写穿透可能让上下两层同时保存一份数据；另一种实现可能主要在下层保存被逐出的状态。两者对总容量、写入流量和缓存命中统计的影响不同。采用哪个实现，应由软件配置决定。

设备是否处于同一个 scale-up 域也很重要。同一个并行组跨出高速互联域后，部分流量进入 scale-out 链路，时延和有效带宽都会改变。模型应根据具体设备放置计算流量经过的路径。

MoE dispatch、P/D 交付、KV offload 和远端加载还可能共用端口或主机通路。把每一类通信都按独占峰值带宽计算，可能低估它们同时活跃时的耗时。粗粒度模型可以先用可配置的带宽分配；需要研究链路竞争时，再显式维护队列和共享服务速率。

交付量也与缓存策略有关。目的端已有一部分兼容状态时，可以传输缺失部分；若 decode 端不保留跨轮状态，则每轮都可能承担很大的交付量。压缩、量化和两端并行布局还会改变交付格式。

资源配比应结合负载。prefill 池太小，会让请求堆积在首轮计算之前；decode 池太小，会延长生成阶段，并让已经建立的状态驻留更久。两边的服务率随各自 batch 和上下文分布变化，不能只按总输入与总输出 token 之比配卡。

异构系统进一步允许 prefill、decode、下层存储使用不同器件。建模时，各组可以引用不同的算子时延表和存储层次，再通过状态交付连接。必要的格式转换需要算子支持和实际时间。

另一个粒度是把同一层中的 attention 与专家计算分到不同设备。它会增加高频交互，尤其要计算每层的固定通信成本。阶段级、层级和存储级异构可以分别研究，不能默认它们具有相同的通信要求。

还要观察系统规模。新增设备既可能增加有效容量和并行度，也可能改变通信域、复制关系与调度方式。把单卡预测直接乘设备数，只适用于资源和工作能近似独立扩展的区域。

12. 软件、CPU 与器件内部的执行效率

调度器决定就绪请求什么时候进入执行，以及这次执行包含哪些 token。continuous batching 会在迭代之间调整成员；chunked prefill 把长输入拆成多个片段；token budget 和请求数上限限制单次 batch。

这些选择会改变算子的 shape。更大的 prefill chunk 可能提高某些矩阵运算的效率，同时延长同一 worker 上其他请求的等待。抢占可以腾出容量，但恢复被抢占请求时还需要处理它的状态。

KV 感知路由也存在具体的取舍。保持会话在原 worker 上，可以提高局部命中；原 worker 过载时，迁移可能降低排队，却增加搬运或重算。好的路由策略需要同时看缓存位置和服务负载。

CPU 侧的前缀查询、请求组织、采样和流式返回也会消耗时间。InferenceX 的 MiniMax-M3 分析指出，所研究配置中的 Dynamo 路由工作量会随存活前缀的数量和长度增长，可能成为瓶颈；宽并行 kernel 与 offload 支持也限制了系统表现。这些观察对应其 2026 年 8 月的配置，适合用来确定模型需要包含哪些行为。MiniMax-M3 系统案例

对于硬件设计，算子内部也值得进一步拆开看。矩阵单元以外，归一化、激活、索引、top-k、归约、转置和量化转换会使用其他执行资源。片上存储容量决定能保留哪些数据，数据布局影响能否有效喂给计算单元。DMA 和通信引擎还会影响搬运与计算能否重叠。

因此，即使两种器件具有相同的标称 FLOPS 和主存带宽，执行这些模块的效率也不一定相同。成熟的 kernel 可能把多个操作融合起来，新器件上则可能暂时分开执行。

在系统模型里，可以先把一部分 host 和启动开销表示为每步开销。但它只能覆盖标定时的规模范围。若路由成本随活跃会话数或前缀长度显著变化，就应把它建成相应变量的函数，必要时加入 CPU 服务队列。

通信实测表和模块级时延表还可能已经包含部分同步或内部拷贝。组合模块之前需要明确每张表计时的起止点，否则容易重复计算。

功耗应覆盖整套被占用资源。某张卡在一个阶段等待，并不意味着它不耗电，也不意味着其购置成本可以忽略。若有状态级功耗数据，可以把计算、访存、通信和等待阶段的能量积分起来；只用 TDP，则得到的是另一种近似。

设计空间还受到物理约束。主存带宽、容量、互联端口、片上存储、计算阵列与封装成本往往相互关联。例如增加内存通道，可能同时增加容量、带宽、PHY 面积和功耗；增加互联资源也会占用芯片与封装资源。

因此，反向问“需要多少带宽才能达到目标”时，要说明其余条件：使用什么模型、多少设备、哪些并行方式、怎样的存储容量和软件能力，以及带宽改变时哪些其他参数一起变化。

把所有参数都当作可以独立调大的旋钮，会得到无法实现的配置。粗粒度模型可以接受用户给出的耦合约束，再在这些约束内寻找可行区域。

15. 一个系统模型怎样组织

前面的内容可以组织成多个相互连接的层次。负载层描述请求与依赖，状态层管理缓存和执行队列，单步层生成当前需要执行的算子与通信，底层负责给这些操作估计时延。

一次事件驱动仿真可以按下面的过程推进：取出最近的事件，更新完成的计算或搬运；让满足依赖的请求进入就绪队列；依据容量与策略准入请求；为可运行的 worker 组 batch，计算下一次完成时间。随后虚拟时钟跳到下一个事件。

这里应保留逐请求的新 token 数、历史长度和状态位置。不同算子可以采用不同聚合方式：共享线性层关注本次 token 总数，attention 关注各请求的上下文，MoE 关注路由后的专家负载。

单步时延由依赖图决定。串行操作相加，可以并行且具有足够资源的分支按完成时刻汇合。两个模块之间“可以重叠”，还不意味着它们能分别以独占资源时的速度完成；若共享带宽、计算资源或缓冲区，需要在模型中体现。

为了快速探索，可以先用闭式模型给出容量要求和计算、访存、通信的下界，淘汰明显不可行的配置，再对剩余候选执行事件重放。缓存相同 shape 的算子查询，也可以减少模型运行时间。

硬件、互联、部署映射和软件栈最好分别描述。这样既可以比较相同软件能力下的硬件变化，也可以比较各系统当前实际可用的部署。后一种结果包含软件成熟度的影响，两种问题都有价值。

DLsim 的设计采用 device、fabric、mapping、stack 四类配置，并把算子时延、单步时延与状态引擎分层。目前已有的内容是这些接口和行为的设计；本文中的新模型分析还需要进一步转成各自的算子与状态描述，不能由一个旧模型的参数替换自动完成。

16. 怎样验证，以及哪些问题仍需额外数据

验证可以从算子开始，再逐步组合到系统。精确命中的算子查询应返回原始测量；插值应在留出的 shape 上检查；跨器件外推应在未参与拟合的器件上比较。每种误差都应按其适用范围报告。

到了单步层，可以检查某个 batch 的实际算子清单、并行后的形状、通信消息和执行依赖。系统层则需要观察吞吐、TTFT、生成时延、缓存层级命中和并发曲线是否同时得到合理解释。

拟合一个最终吞吐值，并不能说明内部过程正确。低估计算、同时高估通信，可能刚好得到相近的总时间。一旦改变 batch 或拓扑，两项误差不再抵消，预测就会偏离。

资源记录有助于诊断，但要注意它们的定义。计算与通信可能重叠，占用率相加可以超过 100%。容量不足通常通过排队、淘汰、重算或限制 batch 影响时间，不能把“容量受限”直接当成一种可独立相加的执行时间。

因此，既要保存各资源的占用与排队状态，也可以做有明确条件的参数扰动：增加一定容量后，缓存和时延怎样变化；只提高链路带宽后，哪段路径缩短；更换路由策略后，命中和负载如何重新分布。这些结果帮助判断模型是否给出了可解释的响应。

数据用途也需要区分。已经参与分析和参数选择的点，可以作为开发诊断。检验预测能力，需要保留未用于这些选择的数据，并在比较之前确定配置、指标和误差口径。如果模型后来修改，修订前后的结果应保留。

不确定性还可能具有相关性。同一个 kernel 在所有层上都被低估，不会因为层数很多就自然抵消。相同的固定开销误差会反复影响每个 decode step。最终区间应反映这些系统性误差，而非仅把每层当成独立噪声。

近期模型还把一些额外问题带进了硬件研究。视觉 Agent 需要图像或视频编码、特征缓存和不同长度的视觉 token；长时间任务会压缩上下文或恢复历史检查点；多模型系统可能给不同节点选择不同模型。这些过程都可以继续扩展到请求图和状态模型，但需要对应的负载数据。

真实系统里的网络、工具执行和任务质量也可能随部署改变。固定 trace 重放通常把工具时间和请求结构当作给定条件，用于研究这些条件下的服务性能。换一个模型之后，它可能生成更多推理 token、调用不同工具或减少重试，这类行为变化需要新的轨迹或显式的行为假设。

对 DLsim，接下来的工作可以从一份确定的 trace、一个具体模型和一套公开部署配置开始：先把请求依赖、算子图、状态位置和逐请求指标连接起来，再逐项加入缓存层级、P/D 分离、跨域通信与其他模型。每次扩展都需要有对应的输入依据，以及能够定位误差的对照数据。
